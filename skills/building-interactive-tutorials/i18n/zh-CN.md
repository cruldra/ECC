# 构建交互式教程

一个主题，一页：一个自带脚本和样式的 HTML 文件，双击即可离线打开。页面分两种，对应两种用途：

- **学习页**：想搞清楚一个项目（多半是开源项目）某一块的内部逻辑。像 Jupyter notebook 一样从上到下阅读：文字格子、代码格子和 3D 演示格子交替出现，带子主题。
- **改造页**：要修复或优化现有代码，现有机制可能被换掉。只有两节，现状和解决方案，各一段简短说明加一段 3D 演示，别的都不放。

两条规则贯穿两种页面：每个数字都来自运行仓库自身的代码，方案部分则来自设计文档；每个外部术语都链接到一个在加入前实际打开过的官方页面。

## 适用场景

- 用户要求制作交互式、3D 或笔记本式教程，讲解仓库中的某个概念：3D 交互教程、可视化讲解、“做一份像 tokenizer.html 这样的教程”。
- 为 `viz/` 下的现有页面添加子主题、章节、代码格子、结构图、卡片组或演示。
- 讲解一个系统的各个部分在运行时如何相互作用（同步进程、Git 服务器、数据库）：用一次录制的真实运行驱动组件图。
- 修复或优化之前：先讲清现有代码怎么运作、哪里出问题，再给方案，做成改造页（梳理现有机制再给方案、现状和方案）。
- 为两种 3D 画面（数据流转、组件图）都无法展示的概念构建新的 3D 画面。

不适用于幻灯片（`frontend-slides`）、视频（`manim-video`、`remotion-video-creation`）或独立图表（`diagram-design`）。

## 工作原理

`${CLAUDE_SKILL_DIR}` 是此 SKILL.md 所在目录。当命令中的路径不是以 `/` 开头时，将 `/assets/` 或 `/scripts/` 之前的部分替换为该目录的绝对路径。

### 1. 先问做哪种页面

动手之前，先用 `AskUserQuestion` 问用户做哪种页面。只有请求里已经点明了种类才跳过。

| 选项 | 什么时候选 | 页面 |
| --- | --- | --- |
| 学习页 | 想搞清楚一个项目某一块的内部逻辑，多半是在学习的开源项目 | 简介（是什么、为什么需要）、核心概念、每个概念一章；每个要点配代码格子、结构图、卡片或演示 |
| 改造页 | 要改现有代码：修 bug、做优化、重做设计，通常对应一张工单 | 现状和解决方案，各一段简短说明加一段组件图演示 |

把最符合请求的选项放第一个并标为推荐。项目的 `viz/README.md` 写明了页面种类时，推荐那一种。这个选择决定第 4 步和第 7 步，其余步骤两种页面都一样。

### 2. 一次性设置 viz/

如果项目里已经有脚手架（`viz/README.md`，有时在 `docs/` 下），先阅读那份 README：它是项目版的这些规则，并列出了已构建的页面。否则复制脚手架并用命令添加依赖，不指定版本：

```bash
cp -R ${CLAUDE_SKILL_DIR}/assets/viz ./viz
cd viz
pnpm init
pnpm pkg set type=module scripts.build="node build.mjs"
pnpm add three
pnpm add -D esbuild shiki
pnpm approve-builds esbuild
pnpm build
```

在 `approve-builds` 允许之前，pnpm 会拒绝运行 esbuild 的安装脚本。`pnpm build` 会生成学习页 `example.html` 和改造页 `example-change.html`，可作为正常工作的页面对照。按选定的页面种类复制对应示例并改成主题名，有了真实页面后删掉两个示例，并更新 `viz/README.md` 中的页面表格。

```
viz/
├── build.mjs                 src/topics/<name>/ → <name>.html，全部内联
├── README.md                 页面列表、写作规则、添加主题的方法
└── src/
    ├── notebook/             所有页面共用的外壳
    │   ├── blocks-3d.js      方块类画面共用的部分：方块、标签、过渡动画、舞台、镜头
    │   ├── flow-3d.js        3D 画面：数据方块在用箭头连起的平台之间移动
    │   ├── graph-3d.js       3D 画面：组件图，各部分逐步点亮
    │   ├── notebook.css      格子排版、结构图和卡片样式、阶段颜色
    │   ├── pipeline-flow.js  数据一站一站排成一条直线时的布局
    │   ├── player.js         演示播放器：翻页、自动播放、离开视口时暂停
    │   └── runtime.js        挂载演示、构建两级目录、在 VS Code 中打开仓库链接
    └── topics/
        ├── example/          学习页
        │   ├── notebook.html     正文格子
        │   ├── main.js           用场景名称注册各个演示
        │   └── steps.js          计算每个演示步骤
        └── example-change/   改造页
            ├── notebook.html     现状和解决方案，各一段话加一段演示
            ├── main.js           给每段演示配上各自的图
            └── steps.js          GRAPH_NOW、GRAPH_NEXT 和两段演示的步骤
```

浏览器拒绝从 `file://` 页面加载本地 ES 模块，因此 `build.mjs` 会用 esbuild 将每个主题的脚本打包成一个内联脚本，并在构建时用 Shiki 为代码着色。将构建好的 `<name>.html` 与源文件一起提交，这样读者无需构建即可打开。

### 3. 研究代码并运行

1. 阅读实现该概念的代码路径：训练或构建它的脚本、配置、数据加载器和调用方。记录将要提及的每个文件和符号；之后要链接到它们。
2. 从仓库根目录用项目的运行器（`uv run python ...`）运行准备展示的每段代码。将输出原样粘贴到 Out 区块中。不要凭记忆编写输出，也不要手动整理。输出是一张表时，改为把各行录成 JSON，排成表格 Out（第 5 步）。
3. 记录将要链接的库的已安装版本（`uv pip show <package>`），确保文档链接与版本匹配。
4. 页面中陈述的每项事实（数量、id、大小、范围）都必须来自这些运行结果或仓库文件。
5. 某个环节录不到时（本机没有模型权重、连不上服务器），用最接近的真实数据代替，并在演示旁的说明文字里写明。MiniMind 本地没有权重，所以解码那一步直接用编码得到的同一串编号，说明里写明真实对话中解码的是模型生成的编号。
6. 正文里的每个结论都要有代码格子的真实 Out 作证据。正文说一来一回一个字都不丢，代码格子就把整串解码的结果打在输入旁边（`print(text, ids, tok.decode(ids))`）；没有 Out 能证明的结论就删掉。

如果概念是一个随操作改变状态的系统，在 `viz/runs/` 下写三个脚本录制一次运行，所有内容都从这次运行里取，这样 Out 区块、正文里的数字和演示就不会对不上：

- `runs/demo.py` 包装被测代码执行命令所用的执行器（沙箱类、`subprocess.run`），把每条命令及其输出记进日志；`frame(label)` 保存那一刻的系统状态（文件、引用、行），连同上一帧以来记下的命令。
- `runs/run_all.sh` 按顺序运行每个代码格子的脚本，把每份输出和全部帧拷进 `runs/out/`。
- `runs/fill_cells.py` 填充模板 `runs/notebook.tpl.html`：`<!--CELL:name-->` 换成代码格子，In 是 `runs/name.py`，Out 是 `runs/out/name.txt`，只做 HTML 转义，该文件是 JSON 行时则排成表格 Out；`{{sha:name}}` 换成运行时以该名字保存的值；帧写成 `trace.js`，由 `steps.js` 导入。

重跑之后，页面上的每个 id 和输出都会自动更新。改模板，不要改生成的 `notebook.html` 或 `trace.js`。

改造页同样要录制现有机制的一次运行，哪怕页面上不放代码格子：演示里的 id、数据行和回复都从这次运行里取。然后读设计文档（spec、工单）拿方案。某个设计选择还没定时，自己选最佳方案画出来，在页面上标「待确认」，并在回复里点出来；不要停下来先问。

### 4. 规划页面大纲

**学习页**按以下顺序分为三个部分：

1. **简介**（`<h2 id="intro">简介</h2>`）：用简单的句子讲它是什么、为什么需要它；比如模型只认数字、不认文字，所以文字要先换成编号。讲的是一个机制时（分词器把文字编码成编号，再解码回文字），紧跟一段演示，演示正下方是一个代码格子，用仓库的代码跑演示里的同一个例子。
2. **核心概念**（`<h2 id="concepts">核心概念</h2>`）：一张 3D 概念图，列出这个主题涉及的全部核心概念以及它们之间的关系：谁产出谁、谁用到谁（第 7 步）。
3. **每个核心概念一章**：概念图上的每个概念各占一个 `<h2>`，只有简介已经讲过的输入和输出除外。同类的变体（ByteLevel、BertPreTokenizer、Metaspace、Whitespace）各占一个 `<h3>`。概念分好几类时（特殊 token：开头结尾和填充、对话标记、功能标记、预留位），章开头先写一段简介，再用一个列表讲各类，每类举一个官方例子。主流做法的内部原理（比如 BPE 怎么训练、怎么编码）是它所属那一章（算法）下的一个 `<h3>`，不单独占一章。

- 讲某种变体（算法、预分词器、解码器）的 `<h3>` 按这个顺序写：先写通用简介，不围着当前项目（它是什么、从哪来并链论文、为什么有用、在库里对应哪个类）；再写 `<p><b>使用场景</b></p>` 列表，只写名字加链接，当前项目排第一；最后是一个演示，原理写进它各步的说明。不写讲原理的列表和注释框：内容放进演示说明，旁枝内容（比如 ByteLevel 怎么把文字转成字节）留给讲它的那一节。演示后面的段落如果和最后一步的说明重复，就删掉。讲机制而不是讲变体的 `<h3>`（整段认出、聊天模板）不写使用场景列表。
- 讲怎么运作的内容不写成代码格子、要点列表、注释框、键值表或 SVG 结构图，一律放进演示的说明。简介里那个代码格子是给它的演示配套的。
- 同一章下的同类条目（比如四种算法）按同一个模板写，演示用同一种布局：都用数据流转图，后排训练、前排编码，不能有一个换成别的画法。章末不加对比小节，各条目的演示已经说清了差别。
- 为什么需要它写在简介里，不单独开一章。各种做法之间的比较（按字节、按整词、按子词）也不是动机，各个做法自己的条目会说清它的不同。

- 每个讲机制的章节或项目（数据进去变了样出来、几个部分互相作用）都要有演示格子。只有文字不算，两条列表项写「编码把文字变成编号，解码再变回来」也不算。
- 标题栏只放 `<h1>`：不放面包屑，也不放副标题，紧跟着是目录。
- `<h2>` 和 `<h3>` 会进入左侧目录，`<h3>` 会缩进显示在对应的 `<h2>` 下方。为其他格子会链接到的每个标题设置 `id`；标题移动时，生成的 id 会改变。
- 库的文件和组件（tokenizer.json）也是核心概念：各占一章，用演示讲它怎么来、怎么用（训练 → 存成文件 → 读回来 → 编码），不做成堆键值表和结构图的附录。

**改造页**只有两个部分，别的都不放：除非用户要求，不放代码格子、表格、卡片和子主题。

1. **现状**（`<h2 id="now">现状</h2>`）：一段简短的话，说代码现在怎么运作、哪里出问题，再放一段组件图演示。
2. **解决方案**（`<h2 id="next">解决方案</h2>`）：一段简短的话，说改了什么、为什么能堵上问题，再放一段组件图演示。

- 标题栏用一行写明工单和问题。
- 细节交给演示。每步说明一两句短话；命令、数据行和 id 放进 `details`，读者点一下就能看。

### 5. 编写格子

```html
<section class="cell text">
  <h2 id="intro">简介</h2>
  <p>…</p>
</section>

<section class="cell code">
  <div class="cell-gutter">In</div>
  <pre class="code-in" data-lang="python">print(tok.convert_ids_to_tokens([1]))</pre>
  <div class="cell-gutter">Out</div>
  <pre class="code-out">['&lt;|im_start|&gt;']</pre>
</section>

<section class="cell demo" data-scene="special-tokens"></section>
```

- 对两个 `<pre>` 块中的 `<`、`>` 和 `&` 进行转义。构建时会在 Shiki 着色前还原 `code-in`；`code-out` 则按原样显示。
- 输出是一张表时（命令行的列表命令、查询结果行），不要把对齐好的文本贴进 `<pre class="code-out">`。命令行按字符数补空格对齐列，浏览器里一个汉字却占两格，列就歪了；值里有换行会把一行拆散；长值会冲出右边。改为录下各行：用命令的 JSON 选项运行（`--json`、`-o json`、`--format json`）；没有这个选项时，让格子的脚本通过命令背后的接口或库取同样的行，打印成 JSON。In 显示实际运行的内容。Out 把每个值原样转义后放进各自的 `<td>`，值里的换行保留：

  ```html
  <div class="code-out out-table"><table>
    <thead><tr><th>key</th><th>value</th></tr></thead>
    <tbody><tr><td>intent_routing.enabled</td><td>true</td></tr></tbody>
  </table></div>
  ```
- 代码格子只有两种：给紧挨在它上面的演示配套，或者它本身就是这一节要讲的内容。别的代码格子删掉。
- 给演示配套的格子紧跟在演示后面，中间不放文字，跑的就是演示里的那份输入。代码按演示的几个部分分段，每段上方单独一行注释（`# 编码：切成 token，再查词表换编号`）。不要把注释写在行尾：一个汉字占两格宽，行尾注释对不齐。Out 里要能找到演示用到的每个数字：编号、表的大小、还原出的原文。
- 代码格子前后不写引导语和预告：不写「演示里的编号都来自真实运行，用 `uv run python` 就能复现」，也不写「后面几节会讲」。别的小节要用某个 Out 里的数字时，自己把数字写出来，不往回引用。
- 文字格子也可以包含 `<table>`、`<p class="note">`，以及 `notebook.css` 中定义的两种布局：
  - `<svg class="diagram">`：手写，`viewBox` 宽度为 1000。方框使用 `box`；为项目实际使用的部分添加 `used`，可选部分添加 `optional`；输入和输出使用 `end`；连接线使用 `edge`，并带有一个页面内 id 唯一的箭头 `<marker>`；文本类为 `name`、`role`、`mono`、`lane`。将方框包在 `<a href="#card-id">` 中可跳转到对应卡片。
  - `<div class="cards">`：每个项目一个 `.card`，并设置各自的 `id`：包含带 `<small>` 代码名称的 `<h4>`、一个 `<p>`，以及一个 `<ul>`；其中的 `<li>` 包含两个子项，分别是名称和含义。`li.pick` 用于标记项目实际使用的内容。
- 仅对项目实际使用的内容添加强调样式（`used`、`pick`）。
- 改造页只用文字格子和演示格子。
- 使用简体中文写作：句子简短直白，每句表达一个事实。术语首次出现时，用日常语言解释。说明原因，不要只解释是什么。
- 正文和演示说明里不写操作提示：不写点哪里、怎么翻页、悬停看什么、点开有什么。读者自己会用页面。
- 同类的几条信息（项目、文件、选项）写成列表，不要串成一句。
- 使用场景列表里，当前项目链到它的源码文件；外部项目链到明确写着它用了这个做法的官方页面（源码或文档）。链接前先打开页面，搜一下做法的名字。几项可以共用一个页面，比如文档里列出哪些模型用了它的那一节，或者一份写明每个模型用什么的源码：HF transformers 的 `convert_slow_tokenizer.py` 里，BertConverter 用 BertPreTokenizer 和 WordPiece，GPT2、Roberta、Qwen2 的 Converter 用 ByteLevel，SpmConverter（T5、ALBERT、XLNet 都继承它）用 Metaspace。
- `steps.js`、`main.js` 和任何新画面中的注释遵循 `writing-code-comments`。

### 6. 将每个术语链接到官方页面

学习页里这是硬性要求：每个专业术语和外部产品首次出现时，都链接到它的官方页面。漏链的术语和写错的数字一样算缺陷。各类术语链接到：

| 术语 | 链接到 |
| --- | --- |
| 机器学习概念 | 中文版 [Google ML 术语表](https://developers.google.com/machine-learning/glossary?hl=zh-cn)，并带上相应锚点，例如 `#token` |
| NLP 概念 | 中文版 [Hugging Face LLM 课程](https://huggingface.co/learn/llm-course/zh-CN/chapter1/1) |
| 库、模型、工具 | 其官方文档、网站或代码仓库；使用与已安装版本匹配的文档 |
| 论文 | arXiv 摘要页 |
| 仓库中的文件 | 相对于构建页面的路径，例如 `../trainer/train_tokenizer.py`；从 `file://` 打开时，运行时会将其转换为 `vscode://` 链接 |

不要链接博客、教程、问答答案或镜像。当已安装版本没有文档（返回 404）时，使用最接近的已发布版本，并对同一文档中的所有链接保持一致。当锚点不存在时，改为链接到附近存在的锚点，或链接到页面本身。

每次构建后，检查构建页面中的所有链接：

```bash
uv run ${CLAUDE_SKILL_DIR}/scripts/check_links.py viz/<name>.html
```

它会获取每个外部页面一次，并检查其状态及页面上用到的每个锚点；同时检查仓库路径是否存在，以及每个 `#id` 是否位于当前页面上。每个失效链接都会打印一行 `FAIL`；只要存在失效链接就以状态码 1 退出。`--offline` 会跳过网络检查。请求带浏览器的 User-Agent，遇到 429 或 503 等待并重试两次，每次等得更久；还是被拒的链接打印成 `LIMITED`，意思是网站多半在限流脚本，不算失败。每个 `LIMITED` 链接都用浏览器打开确认一下。

删掉一个章节时，找出第一次出现在其中并带链接的术语。这些术语在后文再出现时，那里成了首次出现，补上链接。

### 7. 根据真实结果计算演示

演示由一系列步骤组成，每个步骤展示一项变化。学习页里讲机制的演示都用数据流转图，概念图用组件图；改造页的两段演示都用组件图。按读者要看到什么来选布局：

| 布局 | 什么时候用 | 例子 |
| --- | --- | --- |
| 一条直线的数据流转，`createFlowView(pipelineFlow({ stages, rows, arrows, labels }))`，用 `pipeline-flow.js` | 一份数据一站一站往下走，每站换一种形态，「一串变成另一串」也算 | ByteLevel：原文 → 切块 → 字节；解码器：编号 → token → 文字；tokenizer.json：训练 → 存成文件 → 读回来 → 编码 |
| 前后两排的数据流转，`flow-3d.js` 的 `createFlowView(FLOW)`，手摆或用 `trainEncodeFlow` 这类共用函数摆 | 分阶段的过程共用一份产物，或者两趟查同一张表 | 四种分词算法，后排训练、前排编码；编码和解码查同一张词表 |
| 组件图，`graph-3d.js` 的 `createGraphView(GRAPH)` | 几个组件互相调用、写入或指向，每一步在干活的组件不同；学习页里「核心概念」的概念图 | 一轮对话里的同步进程、Git 服务器和数据库；分词器的十个概念以及谁产出谁 |

不管用哪种画面，都要分区。分阶段的过程（先训练、再使用）画成前后两排：第一阶段在后排，第二阶段在前排，两排共用的东西（合并规则、词表）放在一块跨两排的平台上，前一阶段往里写，后一阶段从里面读。每块平台都写标题。不要把几种信息不分区地挤在同一个斜视角里，也不要让中间产物（比如训练记下的规则）只出现在说明里：把它作为方块放到平台上。

组件图只能点亮谁连着谁，画面上看不到数据。要讲数据变成了什么时，比如同一张词表编码正着查、解码反着查，用数据流转图。

不管哪种画面，每一步都有这几个字段：

```js
{
  phase: '合并',                       // 说明栏的阶段标签；新阶段需要在 notebook.css 中设置颜色
  title: '并成一块',
  text: '把挨着的两个 <code>l</code> 并成 <code>ll</code>。',  // HTML，一到三句话
}
```

- 方块和组件的标签：`base` 普通，`focus` 当前步骤关注对象，`new` 刚生成，`done` 已完成，`muted` 未涉及，`unk` 未知，`removed` 即将移除。
- 根据步骤 3 的输出，在数据模块（`steps.js`，或每个子主题一个模块）中计算步骤：要么用 JavaScript 重写小型算法并与库的输出核对，要么将真实 id 和片段复制到常量中，并用注释说明来源。
- 算和画分开。一个纯计算函数产出每一轮或每一步的记录（数到的那一对、记下的规则、套完之后的块），每种画面各有一个函数把这些记录画成自己的步骤。同一个算法的两段演示读同一份记录，数字就不会对不上。同类演示还共用一个布局函数，比如 `trainEncodeFlow(...)`：摆出训练一排和编码一排，可选的中间平台和每行的名字作为参数传入，所有演示的 slot 和箭头名字都一样。
- 在 `main.js` 中通过 `startNotebook({ [id]: { name, tagline, steps, createView } })` 注册每个场景；演示格子的 `data-scene` 就是对应的 `id`。

数据流转图把平台像流程图的节点一样排开，平台之间是地面上的箭头，真实数据是一块块方块，在平台之间移动、拆开、换形。一个 `FLOW` 放整段演示的布局：

```js
export const FLOW = {
  plates: [                                          // 各个环节，从左往右排成一行
    { id: 'text', label: '文字', color: '#4fd1c5', x: -10.5, z: 0.6, w: 5, d: 8.4 },
    { id: 'tok', label: '拆分与合并', color: '#6aa8ff', x: 0, z: 0.6, w: 10.5, d: 8.4 },
  ],
  slots: {                                           // 方块排队的位置，每个一行，居中
    word: { x: -10.5, z: -1.6 },
    vocab: { x: 0.6, z: 0.6, label: '词表' },        // 名字放在这行左边
    ids: { x: 0, z: 2.8, alignWith: 'vocab' },       // 第 i 块对准 vocab 的第 i 块
  },
  arrows: [{ id: 'in', from: 'text', to: 'tok', z: -1.6, label: '输入' }],  // 沿深度 z，从一块平台边沿指向下一块
};

{                                                    // 一步：phase、title、text 之外的字段
  plates: ['tok'],                                   // 点亮的平台，其余变暗
  arrows: ['in'],                                    // 点亮的箭头，有点沿箭头流动
  blocks: [{ id: 'n2', text: '4', tag: 'new', at: 'ids', from: ['merged', 'v2'] }],  // at 是 slot 名
}
```

- 方块的 `id` 整段演示不变，换步时滑到新位置。带 `from` 的新方块从来源方块长出来；这一步不在了的来源方块飞进新方块；其余消失的方块沉下去。同一步里排在前面的方块也能当来源，所以规则在写下的那一步就能长出词表的新一项。
- 后面的步骤留着前面站点的方块。下一站的方块从它们长出来，`from` 指向的方块原地不动；只有真正并成一块的方块才飞进新方块，拆开、查表、交给下一站都不带走来源。否则最后一步前面的平台都空了，看不出整条链。
- `alignWith` 让查表看得见。只画这次用到的表行，按方块的顺序排，每块和它查到的结果都正对着自己那一行。块数和对齐对象不一样多的 slot，按自己的 `x` 居中。
- 两个方向各走一排（`z`），比如编码走后排、解码走前排、表夹在中间，两趟查的是同一排行。
- 给每块平台的标题留位置，标题沿平台后沿铺开：第一行方块离后沿至少 1.5（`slot.z ≥ plate.z − plate.d / 2 + 1.5`）。
- 箭头只沿左右方向，所以同一阶段的平台排成一行。镜头自己按所有平台取景，用窄视角从远处看，画面尺寸变了重新取景；没有镜头坐标要调。
- 注册为 `createView: () => createFlowView(FLOW)`。
- 几站排成一条直线时，用 `pipeline-flow.js` 的 `pipelineFlow({ stages, rows, arrows, labels })` 生成 `FLOW`。`stages` 是从左到右的 `{ id, label, w, rows, color }`，每站可以有不同的行数；`arrows` 是相邻两站之间箭头上的字；`labels` 给某一站的各行起名（`{ letters: ['「hello」', '「hell」'] }`）。slot 名是平台 id 加行号（`letters0`），箭头 id 是 `from>to`；它会给每个标题留位置，颜色按顺序轮换。

`graph-3d.js` 里的组件图画面用一个 `GRAPH` 摆出整个系统，每个演示点亮其中的一部分：

```js
export const GRAPH = {
  groups: [{ id: 'data', label: '数据', color: '#e2b93b', x: 0, z: 3.5, w: 25, d: 5.2 }],  // 带标题的地面平台
  nodes: [{ id: 'counts', kind: 'table', label: '次数表', sub: 'counts', x: -2.75, z: 3.5,
            desc: '一个字母一行，记它出现几次。', code: 'src/topics/example/steps.js', href: '#split-merge' }],
  edges: [{ id: 'point', from: 'top', to: 'counts', label: '指着', desc: '只是指着一行。', dashed: true }],
};

{                                                 // 一步：phase、title、text 之外的字段
  nodes: { count: 'active', counts: 'new' },      // active、new、gap、base、off；没列出的组件变暗
  edges: [{ id: 'write', label: '写次数', tone: 'new' }],  // 点亮，有点沿线流动
  badges: { counts: '4 种字母' },                  // 名牌的第三行，或 { text, tone }
  details: { counts: ['h  1 次', 'e  1 次'] },    // 提示框和面板显示的几行
  focus: ['count', 'counts'],                     // 镜头取景要看全这些组件
}
```

- `x` 向右，`z` 朝向读者。组件宽 3.4、深 1.7：组件之间相隔约 5.5，并在每个分组第一个组件的左边给分组标题留出位置。
- 种类：`process` 是圆角方块，`store` 是圆柱，`table` 是带环的圆柱，`ref` 是紫色方块。在 `GRAPH.kinds` 里添加种类，在 `GRAPH.tones` 里添加状态色。
- 悬停组件显示它的 `desc`、`code` 和 `details` 的前四行，悬停连线显示它的 `label` 和 `desc`；单击固定一个显示全部行的面板；双击把镜头拉回这一步的取景。
- 注册为 `createView: () => createGraphView(GRAPH)`，并给它的演示格子加上 `style="--stage-height: 560px"`，让名牌放得下。
- 学习页用组件图画「核心概念」的概念图：一个核心概念一个组件，`sub` 写真实数字（6400 行、6108 条）；一种关系一条连线，标上这层关系（学出 token、按顺序套用、占 0–35 号）。每个组件写 `href`，即讲它的那一章的 `#id`；点开的面板里会多一个「去讲它的那一节 →」链接，悬停提示不放，因为鼠标够不着。
- 概念图的第 1 步看全貌，所有组件都是 `base`，`focus` 是全部组件。之后每步点亮一块，顺序跟页面章节一致，说明末尾写 `→ <a href="#章节">名字</a>`。每一章都有自己的一步，新增一章就补一步。演示格子写 `style="--stage-height: 600px"`，分组平台按组件的范围定宽：镜头只按组件取景，平台比组件宽出太多，标题就出了画面。
- 两种画面都无法展示该概念时，另写一个画面，使其返回 `mount(stage)`、`render(step, { reset })` 和 `setActive(active)`，并保留播放器。由方块构成的画面在 `blocks-3d.js` 的 `createBlockScene` 上搭，那里已有舞台、镜头、过渡动画和 `syncBlocks`。

改造页画两张图，`GRAPH_NOW` 画现有机制，`GRAPH_NEXT` 画方案，做法见 `example-change/steps.js`：

- 两张图里都有的组件保持同一个 `id`、同一个位置，读者看到的是同一处在变。方案去掉的组件不放进 `GRAPH_NEXT`；新的或改过的组件在方案步骤里用 `new`。
- 流程对得上的地方（一轮对话、一次预览、一次恢复），方案的步骤跟着现状的步骤走，两段演示能一步一步对照。
- 现状演示里的每个问题用 `gap` 点亮，最后一步把所有问题一起点亮。方案演示停在把这些问题都堵上的那一步。
- 方案数据取自设计文档：名字、规则、上限。复用现状那次运行的 id（提交号、会话 id）让它具体，并在说明里写明这一步是设计，不是运行。
- 每段演示注册自己的图：`createView: () => createGraphView(GRAPH_NOW)` 和 `createView: () => createGraphView(GRAPH_NEXT)`。

**子主题。** 请求：“加一个子主题讲解这几个 special tokens”。

## 常见错误

| 错误 | 修正方法 |
| --- | --- |
| 凭记忆编写 Out 区块，或手动整理输出 | 重新运行代码片段，并原样粘贴输出 |
| 链接到博客，或链接到没有实际打开过的锚点 | 仅使用官方页面；运行 `check_links.py` |
| 已安装版本的文档返回 404 | 使用最接近的已发布版本，并在所有链接中保持一致 |
| 代码格子中 `<` 未转义，导致浏览器将其解析为标签 | 写作 `&lt;`、`&gt;`、`&amp;` |
| 新阶段名称没有对应颜色 | 在 `notebook.css` 中添加 `.demo-meta .phase[data-phase="…"]` |
| 方块 id 在各步骤间变化，导致方块跳跃而不是滑动 | 整个演示中每个片段都使用同一个 id |
| 一个步骤中包含多项变化 | 拆分；一步只包含一项变化 |
| 截图时页面仍在滚动 | 先使用 `behavior: 'instant'` 滚动 |
| 文字溢出结构图方框 | 加宽方框后重新截图 |
| 链接到没有 `id` 的标题 | 为标题添加 `id` |
| 将库参考资料列为附录 | 给它一章，用演示讲它怎么来、怎么用 |
| 编辑构建后的 `<name>.html` | 编辑源文件并重新构建 |
| 把命令行的表格贴进 `<pre class="code-out">`：中文把列挤歪，多行的值把一行拆散 | 把各行录成 JSON，写成表格 Out（第 5 步） |
| Out 区块、正文和演示取自不同的运行，数字对不上 | 录制一次运行，三者都从它生成（第 3 步） |
| 名字平铺在组件顶面，斜着看读不出来 | 把名牌画成始终朝向镜头的 sprite |
| 步骤数据放在叠在名牌上方的第二个 sprite 里，俯视时两者重叠 | 把数据并进同一块名牌，作为第三行 |
| 广角镜头让近处组件显得很大、远处很小 | 用 24° 的窄视角，从更远处看 |
| `check_links.py` 把 GitHub 文件页（`/blob/`）列为 `LIMITED` | GitHub 在限流脚本；用浏览器打开，能打开就保留这个链接 |
| 没问做哪种页面就开始做 | 先问（第 1 步）；两种大纲不一样 |
| 改造页越写越长，长出代码格子、表格和子主题 | 只留两段话和两段演示；细节放进 `details` |
| 方案图重新布局，和现状图对不上 | 共有组件保持同一个 `id` 和位置 |
| 为了演示编出方案里的数字 | 从设计文档取，复用现状那次运行的 id |
| 还没画就先停下来问没定的设计选择 | 选最佳方案、标「待确认」，在回复里点出来 |
| 一个机制只用文字或两条列表项讲，没有演示 | 加一个演示格子；学习页里每个机制都要有 |
| 学习页标题下放面包屑或副标题 | 只留 `<h1>` 和目录 |
| 数据经过几个环节的过程画成组件图：读者看到谁和谁相连，看不到什么变成了什么 | 用数据流转图 |
| 查表的结果和它的表行离得很远 | 只画用到的行，按方块顺序排，并设置 `alignWith` |
| 运行录不到的环节，悄悄补上数据 | 用最接近的真实数据，并在正文里写明（第 3 步） |
| 正文里的结论（如「一来一回一个字都不丢」）在任何 Out 里都看不到 | 在代码格子里打出证据，如 `tok.decode(ids)`，或者删掉这句结论 |
| 新写的方块类画面复制了舞台、镜头或过渡动画 | 在 `blocks-3d.js` 的 `createBlockScene` 上搭 |
| 把某个算法的原理（比如 BPE 怎么训练、怎么编码）写成「工作原理」章 | 第二章改为「核心概念」，用概念图；算法放进它所属的子主题，作为一个 `<h3>` |
| 名义上讲动机的章节，实际在比较各种做法 | 为什么需要它写进简介；各个做法自己的条目说清它的不同 |
| 删掉一个章节，把某个术语唯一的链接也一起删了 | 给该术语新的首次出现补上链接（第 6 步） |
| 正文或演示说明里写操作提示，比如「点一个概念看说明」「用 ← → 翻页」 | 删掉；读者自己会用页面 |
| 讲做法的子主题一开头就围着当前项目写，或者把几个项目串成一句 | 先写通用简介，再写使用场景列表，然后讲原理（第 4 步） |
| 原理写成要点列表，再在演示旁加注释框 | 放进演示的各步说明；旁枝内容留给讲它的那一节 |
| 演示不分区，中间产物（合并规则）只在说明里提到 | 每个阶段一排带标题的平台，把中间产物作为方块放到平台上 |
| 同类子主题画法不一样，一个用数据流转图、一个换了别的画法，或者章末加一个对比小节 | 全部用同一个模板、同一个布局函数；不加对比小节 |
| 使用场景链到一个根本没提这个做法的页面 | 打开页面搜一下做法的名字，链一个写明了的页面 |
| 概念图里有的概念没有自己的一章 | 补上这一章，再在概念图里补一步 |
| 演示放到最后一步，前面的平台都空了 | 每一站的方块都留着，下一站的方块从它们长出来 |
| 代码格子前后写引导语或预告（「可以这样复现」「后面几节会讲」），或者代码格子既不给演示配套，也不是这一节的内容 | 删掉；给演示配套的格子紧跟演示，演示有几部分，代码就分几段，每段一行注释（第 5 步） |

## 完成前检查

- [ ] 页面种类是用户选的，或请求里已经点明。
- [ ] 每个 Out 区块都来自真实运行，并原样粘贴；正文中的每个数字都与运行结果或仓库内容相符。
- [ ] 学习页：标题下只有 `<h1>`，简介讲清是什么和为什么需要，没有单独的动机章，「核心概念」概念图的每个组件都链到讲它的那一章，图上每个概念都有自己的一章，讲做法的子主题按通用简介、使用场景、原理的顺序写，没有操作提示，每个机制都有演示，每个专业术语都有官方链接，每个结论都有 Out 作证据，运行录不到的环节都在正文里写明。
