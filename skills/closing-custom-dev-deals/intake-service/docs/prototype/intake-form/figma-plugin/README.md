# 需求信息登记表 · Figma 原型插件

在 Figma 桌面版里画出这套通用登记表：客户点一条链接，在手机上三步填完。
同时画了桌面单页版作为对照，两种版式选一个。

## 画了什么

| 画板 | 内容 | 要定的事 |
|---|---|---|
| 开始 | 品牌条、一句话说明、三条填表须知、开始按钮 | 第一屏能不能让人愿意点「开始填写」 |
| 第 1 步 · 企业信息 | 公司名称 / 城市 / 主营业务 + 行业、企业规模标签，按钮置灰 | 必填没填完时按钮该不该灰 |
| 第 1 步 · 企业信息 · 已填 | 同上，填好的样子 | 填过的值怎么显示 |
| 第 1 步 · 未填必填项 | 公司名称报错 | 报错提示写法 |
| 第 2 步 · 关键岗位与流程 | 预置两个岗位卡（岗位名称 + 日常工作流程），可添加 | 预置两个够不够、流程框要多大 |
| 第 3 步 · 期望 AI 赋能的场景 | 预置两张场景卡（场景名称 / 现状 / 预期），可添加 | 现状与预期分两栏写得下吗 |
| 提交完成 | 收到确认 + 下一步说明 | 提交后告诉客户什么 |
| 桌面 · 单页 | 1200 宽两栏，一页填完 | 分三步 还是 一页到底 |

## 导入与运行

1. 打开 Figma 桌面版，进入任意一个 Design 文件
2. `Plugins > Development > Import plugin from manifest…`，选本目录的 `manifest.json`
3. `Plugins > Development > Intake Form Design Lab` 运行

每次运行新建一页，不覆盖已有内容；同名时页名后缀 `2`、`3`。

## 运行条件

- 中文字体：`PingFang SC` / `Noto Sans CJK SC` / `Noto Sans SC` / `Source Han Sans SC` 至少有一个可用，否则在建页之前就报错退出
- 文件还有剩余页面配额（起步版文件有上限）

## 生成内容

三个组件集，画板全部由它们的实例拼成，改主组件会传播到每一块画板：

- `Intake / Field` — `State=empty | filled | error`
- `Intake / Chip` — `State=off | on`
- `Intake / Progress` — `Step=1 | 2 | 3`

岗位卡和场景卡不是组件集，共用 `entryCard`：卡里的单行输入复用 `Intake / Field`，多行区是普通框。
外层普通框，方便客户添加任意多张。

## 原型交互

七条链接：开始 → 第 1 步 → 已填 → 第 2 步 → 第 3 步 → 提交完成 → 回到开始，
外加桌面单页 → 提交完成。「未填必填项」那块是死胡同，按钮不可点，这就是它要表达的事。

演示入口是「开始」画板。

## 题目从哪来

题目全是通用的：这一步发生在我们还不知道客户是哪一行的时候，所以每一道都问客户张口就能答的事实，
不需要他事先准备。三步是上限，再多人就填不完直接跑了。

**输入框里不写引导语。** 「营业执照上的全称」「给个区间就行」这种提示，客户读起来像我们在套他的信息。
标签写清楚就够了，剩下让他自己填。

**全篇用书面语。** 「你们卖什么」写成「主营业务」，「最烦的三件事」写成「待解决的问题」。
这份表发给的是甲方决策人，口语显得不专业。

不问数据清单、不问在用什么系统、不问合同金额和单量。第一次接触问这些，客户要么答不上来，要么觉得我们在摸他的底。

**第 2 步问岗位和流程**，因为这是出原型最直接的养料：知道有哪些角色，才知道界面该分成谁看什么。

**第 3 步问场景，每个场景写现状和预期两栏**。只写预期我们不知道要改哪一段，两边对着写才定得下范围。两步都预置两个位子，不够客户自己加。

## 本地检查

```bash
node --check code.js
node --test test.js
```

测试跑的是离线假文档，只验结构、数据、连线和排版不重叠，**不代表视觉通过**。
视觉要在 Figma 里看。
