# 编写需求规格说明书

把客户说的话整理成甲方能逐条确认的需求规格说明书，最后交一份干净的 Word。

## 何时使用

- 有客户会议、录音、逐字稿、聊天导出或笔记，用户要给甲方出第一版或下一版需求文档。
- 甲方回复了待确认问题，要据此更新需求说明书。
- 不用于设计文档（`spec`）、实施计划（`writing-plans`），也不用于还没想清楚的点子（先走 `grilling`）。报价、技术方案和合同归 `closing-custom-dev-deals`，它的闸门 1 要求先有这份文档。

## 工作方式

自带文件：

| 文件 | 用途 |
|---|---|
| `references/srs-outline.md` | 章节大纲、需求条目格式、附录各列 |
| `scripts/condense_srt.py` | SRT 压成每分钟一行 |
| `scripts/strip_annotations.py` | 内部版生成甲方版；`--check` 检查残留 |
| `scripts/md2docx.py` | Markdown 转带框线表格的 Word |

### 1. 拿到原话

- 只有音频或视频：先用 `transcribing-audio` 转文字。
- 有 SRT 文件：压缩后一次就能读完整场会议。每行以 `[mm]` 开头，表示第几分钟，之后用作需求的出处。

  ```bash
  uv run --script ${CLAUDE_SKILL_DIR}/scripts/condense_srt.py meeting.srt -o /tmp/<project>/minutes.txt
  ```

- 读完整份逐字稿，不要抽读。语音识别会出同音错字，按上下文改正（自由化部署 → 私有化部署，PTF → PDF），改不了的词记下来，写进最后的汇报。
- 文档抬头从固定来源取，这三项不留【待填写】：
  - 乙方：取 `closing-custom-dev-deals` 保险箱里的公司全称。只解出这一份，保险箱里的报价数据与本文无关。

    ```bash
    bash ${CLAUDE_PLUGIN_ROOT}/skills/closing-custom-dev-deals/scripts/vault.sh show company-profile.md
    ```

    报“还没存口令”时，让用户跑一次 `vault.sh unlock`。不要按项目目录名猜公司名。
  - 甲方：取项目 `README.md` 里“客户：”那一行，用用户对客户的叫法。没有 README 或没有这一行时问用户一次，再把这一行写进 README（没有就新建），下一版直接读到。
  - 文档编号：`HK-<项目代号>-SRS-<序号>`。项目代号是项目目录名去掉连字符后转大写（`ai-civics` → `AICIVICS`）；序号按本项目第几份需求说明书从 `001` 起。项目里已有需求说明书（`docs/*_需求规格说明书_*.md`）的沿用原编号，升版本不换编号。

### 2. 把内容分类

动笔前把每个要点归类：目标和痛点；范围（一期、以后、不做）；用户；功能；数据和资料；限制（法规、部署、归属）；分工和后续动作；钱和时间。再判断每个要点是甲方说过的（已确认）、你推断的（推断），还是只有甲方能提供的（待提供）。

### 3. 写内部版

按 `references/srs-outline.md` 逐章写 `docs/<项目>_需求规格说明书_V0.1.md`。某节确实不适用才删；项目既不训练也不调用模型时删掉 3.6。

- 每条需求占表格一行：编号、需求、优先级、状态、来源。大纲里写了编号前缀和各取值的含义。
- 每条需求一句话，以“系统应”开头，测试人员能验证。
- 推断出来的内容不能写成甲方说过的：标“推断”。你补充的术语释义加“（释义为乙方推断）”。
- 甲方没给的数字（响应时间、准确率、并发数）是乙方建议值：在表格前写明，并在附录 A 里再问一次。
- 用甲方自己的说法，句子短。

附录是甲方真正要动手处理的部分：

- **A 待确认问题**：每个缺口都附一个建议答案（乙方建议），并写明会卡住哪些需求编号。给建议答案，不问开放式问题。
- **B 沟通共识**：分工、方向、后续动作，写明责任方和时间。
- **C 甲方需提供的资料**：每项资料、用途、什么时候交。

如果这是一单生意，还要覆盖 `closing-custom-dev-deals` 闸门 1 的八个问题，预算除外。

### 4. 不进甲方版的内容

| 内容 | 改写成 |
|---|---|
| 口头说过的价格、预算区间、报价 | 费用和周期另见报价方案。这里出现的任何数字都等于书面报价 |
| 工期 | 只在附录 A 的问题里引用沟通时的原话，不写成承诺 |
| 归属和保密 | 写明约定的方向，后面加“以合同为准” |
| 标准名称、条款号、“模板”字样 | 不写：甲方要的是内容，不是出处 |
| 状态、会议分钟、录音文件名 | 不写：只留在内部版 |

### 5. 生成甲方版

```bash
uv run --script ${CLAUDE_SKILL_DIR}/scripts/strip_annotations.py docs/<项目>_需求规格说明书_V0.1.md docs/<项目>_需求规格说明书_V1.0.md
```

脚本删掉“状态”“来源”两列和所有 `[mm]` 标记，不覆盖已有文件，并打印仍含内部用语（推断、会上、录音、ISO、模板……）的行。这些行手工改写：

1. 版本改为 V1.0；修订记录写“根据 <日期> 双方需求沟通编写第一版”；删掉“结构依据”一行。
2. 把“阅读说明”换成三条“说明”：请审阅批注；附录 A 和 C 确认后据此出方案和报价；费用和周期见报价方案。
3. 参考资料里删掉标准，“会上”改成“沟通时”或直接删掉。
4. 运行 `uv run --script ${CLAUDE_SKILL_DIR}/scripts/strip_annotations.py --check <V1.0 文件>`，直到退出码为 0。

保留内部版，以后甲方问“我什么时候说过”时用得上。

### 6. 导出 Word

```bash
uv run --script ${CLAUDE_SKILL_DIR}/scripts/md2docx.py docs/<项目>_需求规格说明书_V1.0.md
```

需要 pandoc（`brew install pandoc`）。每张表都占满版心、带框线、表头浅色底，列宽按内容分配。不生成目录：pandoc 的目录域会让 Word 打开时询问是否更新域，用户需要目录就告诉他从“引用 → 目录”插入。删掉旧的甲方版 `.docx`，免得发错。

在 macOS 上用 `qlmanage -t -s 1400 -o <dir> <file>.docx` 渲染第一页，看 PNG 里的标题、抬头表格和框线。这只检查了第一页，汇报时要说明。

### 7. 汇报

第一行给 Word 路径。然后写用户要拍板的事（哪些内容没写进去、为什么，比如预算）、要复核的推断、逐字稿里没能确认的词，以及没验证的地方。

## 示例

一场 41 分钟会议的 SRT 压成 42 行。内部版 V0.1 有 60 条需求、12 个待确认问题，每个都附建议，没写预算。`strip_annotations.py` 生成 V1.0 并标出 24 行；改写后 `--check` 退出码为 0，`md2docx.py` 生成带 27 张框线表格的 Word。
