# 应用设计模式

设计模式是给反复出现的设计问题起了名字的解法。只有当它消除了代码眼下正在付出的代价时才值得用：每加一个变体都要改同一个大类、同一段分支被复制到每个调用方、每种组合一个子类。这个技能先找出这个代价，再挑能消除它的最小模式，或者干脆不用模式。

## 何时使用

- 重构这样的代码：每加一个变体、渠道、状态或供应商，都要改同一个函数或类。
- 审查这样的改动：往长分支里再加一个 `elif`/`case`，给构造函数再加一个可选参数，或为一种组合再加一个子类。
- 有人问"这里该用哪个模式""这是不是过度设计""用设计模式优化一下这段代码"。
- 拿掉一个已经不划算的模式。

它不决定新文件放哪、叫什么（见 `organizing-code`），不管整个应用的架构（见 `hexagonal-architecture`），也不管框架惯用法（见各个 `*-patterns` 技能）。

## 工作方式

### 1. 先说清痛点，再谈模式

提建议之前，先按这个句式写一句话："每次新增或修改 X，都要改 Y。"X 是变化的方向，Y 是受罪的代码。用代码或它的历史（`git log -p --follow <file>`）来佐证：每月多一个分支的地方才是真正的变化方向，三年前写完就没动过的分支不是。写不出这句话就停下，没有什么需要模式来解决。

### 2. 过门槛

四项检查全部通过才用模式：

1. **变体够多。** 代码里已有三个变体，或者两个加一个已经排期的第三个。接口背后只有一个实现，是投机性的泛化。
2. **变体因不同原因而变。** 如果它们总是一起改，就放在一起。
3. **语言特性没有现成解法。** 见第 4 步。
4. **下一次修改变小了。** 数一数加下一个变体前后要碰的文件和函数。数量没降，模式只是把代码挪了个地方。

某项不通过时，答案通常是普通重构：提取方法、加卫语句、用查找表、引入参数对象。直说即可，"不用模式"也是合格的结论。

### 3. 把信号对应到模式

| 代码里的信号 | 首选模式 | 对照 |
| --- | --- | --- |
| 一个按类型或模式分支的 `if`/`switch` 从几种算法里选一种 | 策略 | 如果分支还会切换模式，看状态 |
| 同一个状态字段在许多方法里被检查；状态转换四处分散 | 状态 | 如果没有状态转换，看策略 |
| 调用方按条件选一个具体类来构造 | 工厂方法 | 如果几种产品必须配套，看抽象工厂 |
| 同一系列的对象不能和另一系列混用（主题、厂商、平台） | 抽象工厂 | 如果只有一种产品，看工厂方法 |
| 构造函数有很多可选参数，或者组装要分步进行 | 生成器 | 命名参数或默认参数 |
| 子类只是初始值不同；配置好的对象要被复制 | 原型 | 带预设的工厂 |
| 代码需要恰好一个共享实例 | 在组合根创建一个实例并注入 | 单例，仅在无法注入时 |
| 第三方或遗留接口和调用方代码对不上 | 适配器 | 包装整个子系统时，看外观 |
| 类的数量沿两个维度相乘（`Shape × Renderer`） | 桥接 | 某一维度只是一种算法时，看策略 |
| 部分与整体组成的树，叶子和分组要同样对待 | 组合 | 对数据做普通递归 |
| 可选行为围绕同一接口层层叠加（重试、缓存、日志）；每种组合一个子类 | 装饰 | 一个包装层控制访问时，看代理 |
| 调用方针对几个子系统类重复同样的多步调用序列 | 外观 | 这些类彼此调用时，看中介者 |
| 海量几乎相同的对象耗尽内存 | 享元 | 驻留或缓存 |
| 访问需要在同一接口后做延迟加载、缓存、权限检查或远程调用 | 代理 | 行为需要叠加时，看装饰 |
| 请求要经过一系列检查或处理器，其中任何一个都可能拦下它 | 责任链 | 在循环里依次执行一组函数 |
| 操作需要排队、重试、记录、定时执行或撤销 | 命令 | 不需要撤销和持久化时，用闭包 |
| 遍历代码到处复制，或暴露了集合的内部结构 | 迭代器 | 语言自带的迭代协议 |
| 许多组件直接互相引用（表单字段、控件） | 中介者 | 一对多的流向时，看观察者 |
| 撤销或回滚需要私有状态的快照 | 备忘录 | 用逆操作实现撤销的命令 |
| 一处变化要通知一组会变动的依赖方，而源头把它们写死了 | 观察者 | 依赖方之间还要协调时，看中介者 |
| 几个类执行同一套算法骨架，只有几步不同 | 模板方法 | 想用组合来变化步骤时，看策略 |
| 许多不相关的操作作用于一个稳定的类层次（AST、文档） | 访问者 | 对封闭联合类型做模式匹配 |

写代码前先读模式卡片。每张卡片列出信号、重构步骤、代价和易混模式：[创建型](references/creational.md)、[结构型](references/structural.md)、[行为型](references/behavioral.md)。

### 4. 优先用语言自带的写法

许多经典模式是用类把现代语言直接提供的能力写出来。用能保留同一个接缝的最轻写法，只有出现对应的触发条件时才换成类的写法：

| 模式 | 先用更轻的写法 | 何时换成类的写法 |
| --- | --- | --- |
| 策略 | 一个函数，或从键到函数的映射 | 某个变体带有配置或几个相关方法 |
| 命令 | 闭包 | 需要撤销、持久化或历史记录 |
| 迭代器 | 生成器或语言的可迭代协议 | 语言自带时永远不用 |
| 观察者 | 平台的事件发射器、信号或回调列表 | 订阅者需要带类型的事件和生命周期控制 |
| 模板方法 | 接收可变步骤的高阶函数 | 子类已经存在且共享状态 |
| 装饰 | 函数包装或中间件 | 被包装对象暴露了很多方法 |
| 生成器 | 关键字或默认参数、`dataclasses.replace`、对象展开、Kotlin `copy` | 步骤有顺序规则或跨字段校验 |
| 原型 | `copy.deepcopy`、`structuredClone`、数据类的 `copy()` | 副本不能共享其拥有的资源 |
| 单例 | 模块级实例，或 DI 作用域里的单个实例 | 能注入就永远不用 |
| 工厂方法 | 工厂函数或注册表映射 | 子类必须覆盖创建逻辑 |
| 状态 | 从（状态，动作）到下一状态的转换表 | 每个状态还会改变其他方法的行为 |
| 访问者 | 对封闭联合类型做穷尽的 `match`/`when`/`switch` | 语言没有穷尽匹配 |

### 5. 小步重构

1. 先在公开入口上用测试钉住当前行为。没有测试就先写特征测试（`tdd-workflow`）。
2. 引入接缝（接口或函数类型），让现有行为作为它唯一的实现。测试保持通过。
3. 每次只把一个变体从分支里移到它自己的实现中。每移一次就跑一次测试。
4. 在同一次改动里删掉旧分支和临时开关。不留两条路径。
5. 在一个地方（组合根、工厂、注册表）装配各个变体，而不是在每个调用方。

### 6. 了解每个模式的代价

- 外观和中介者会长成上帝对象。一旦承担了第二个职责就拆分。
- 单例隐藏依赖、破坏测试隔离。改用注入。
- 访问者让每个新元素类都要改所有访问者。只在类层次稳定、操作常变时使用。
- 装饰栈依赖顺序且难调试。在一个地方构建整个栈。
- 观察者不保证通知顺序。订阅者之间不能互相依赖。
- 抽象工厂和桥接会增加平行的类层次。只为真实存在的系列或维度使用。
- 模板方法把子类锁定在一个骨架上。子类把某一步覆盖成什么都不做，说明继承关系错了。

### 7. 分清长得像的模式

有几个模式结构相同，都是把工作委派给另一个对象，区别只在意图。提议时要说出意图：

- **策略、状态、桥接、命令。** 策略替换完成同一件事的方式，各变体互不知晓。状态的各变体彼此知晓，并在彼此之间切换上下文。桥接把两个独立维度拆开，让各自单独扩展。命令把一次调用变成可以存储、排队或撤销的对象。
- **适配器、代理、装饰、外观。** 适配器给对象换一个接口。代理保持接口不变并控制访问。装饰保持接口不变、增加行为、可以叠加。外观在许多对象之上提供一个新的、更简单的接口。
- **工厂方法、抽象工厂、生成器、原型。** 工厂方法通过可覆盖的方法造一种产品。抽象工厂造一整套配套产品。生成器分步造一个复杂产品。原型复制一个配置好的实例。
- **模板方法和策略。** 模板方法通过继承变化步骤，按类固定。策略通过组合变化步骤，运行时可切换。
- **外观和中介者。** 外观是单向的：子系统不知道它存在。中介者夹在只通过它通信的同级对象之间。
- **观察者和中介者。** 观察者是动态的一对多订阅。中介者集中处理多对多的协调。

### 8. 汇报提议

每一处都汇报：

- **痛点**：第 1 步的那句话，附 `file:line`。
- **模式**：名字和写法，语言自带还是类。
- **门槛**：四项检查各自为什么通过。
- **代价**：新增的类型或文件，以及否决了哪个易混模式、为什么。
- **步骤**：第 5 步的流程落到这段代码上的具体做法。
- **下一个变体**：改完后再加一个变体是什么样子，例如一个新函数加一行注册。

没过门槛的地方列在 **不用模式** 下，并给出适用的普通重构。

## 示例

### 用查找表实现策略（Python）

痛点："每加一个承运商都要改 `quote()`。"

```python
def quote(order: Order, carrier: str) -> Decimal:
    if carrier == "ups":
        return Decimal("5") + order.weight * Decimal("1.2")
    elif carrier == "fedex":
        return Decimal("7") + order.weight
    elif carrier == "dhl":
        return max(Decimal("10"), order.weight * Decimal("1.5"))
    raise ValueError(f"unknown carrier: {carrier}")
```

已有三个承运商，第四个已经排期，门槛通过。每个承运商一个函数就够了，暂时不需要类：

```python
from collections.abc import Callable
from decimal import Decimal

Quote = Callable[[Order], Decimal]

def _ups(order: Order) -> Decimal:
    return Decimal("5") + order.weight * Decimal("1.2")

def _fedex(order: Order) -> Decimal:
    return Decimal("7") + order.weight

def _dhl(order: Order) -> Decimal:
    return max(Decimal("10"), order.weight * Decimal("1.5"))

CARRIERS: dict[str, Quote] = {"ups": _ups, "fedex": _fedex, "dhl": _dhl}

def quote(order: Order, carrier: str) -> Decimal:
    strategy = CARRIERS.get(carrier)
    if strategy is None:
        raise ValueError(f"unknown carrier: {carrier}")
    return strategy(order)
```

下一个变体：一个函数加一条字典项，`quote()` 不用动。当某个承运商需要自己的配置（比如 API 客户端或费率表）时，再换成策略类。

### 用转换表实现状态（TypeScript）

痛点："每加一个订单动作，都要在 `pay()`、`ship()`、`cancel()` 里重复状态检查。"

```typescript
type Status = "draft" | "paid" | "shipped" | "cancelled";
type Action = "pay" | "ship" | "cancel";

const transitions: Record<Status, Partial<Record<Action, Status>>> = {
  draft: { pay: "paid", cancel: "cancelled" },
  paid: { ship: "shipped", cancel: "cancelled" },
  shipped: {},
  cancelled: {},
};

class Order {
  status: Status = "draft";

  apply(action: Action): void {
    const next = transitions[this.status][action];
    if (!next) throw new Error(`cannot ${action} a ${this.status} order`);
    this.status = next;
  }
}
```

这张表把所有允许的转换集中在一处。只有当每个状态还会改变定价、退款或通知的行为，否则状态检查会扩散到那些方法里时，才换成每个状态一个类。

### 否决：只有一种产品的工厂

一个永远只返回 `EmailNotification` 的 `NotificationFactory` 没过门槛第 1 项。把构造调用内联，删掉这个工厂。等第二个渠道真正上线时，再引入工厂函数。
