# Aside 命令

在任务进行中提出问题，立即获得聚焦的回答——然后从刚才中断的地方继续。当前任务、文件和上下文绝不会被修改。

## 何时使用

- Claude 工作期间你对某件事感到好奇，但又不想打断工作节奏
- 你需要快速解释 Claude 当前正在编辑的代码
- 你想在不让任务脱轨的前提下，就某个决定听取第二意见或获得澄清
- 在 Claude 继续之前，你需要先理解某个错误、概念或模式
- 你想问一个与当前任务无关的问题，但又不想另起一个新会话

## 用法

```
/aside <你的问题>
/aside 这个函数到底返回什么？
/aside 这个模式是线程安全的吗？
/aside 为什么这里我们用 X 而不是 Y？
/aside foo() 和 bar() 有什么区别？
/aside 我们刚加的 N+1 查询需要担心吗？
```

## 流程

### 第 1 步：冻结当前任务状态

在回答任何内容之前，先在心中记下：
- 当前活跃的任务是什么？（当时正在处理哪个文件、功能或问题）
- 调用 `/aside` 的那一刻正在进行哪个步骤？
- 接下来原本要做什么？

在旁支问答期间，切勿触碰、编辑、创建或删除任何文件。

### 第 2 步：直接回答问题

以最简洁但仍完整、有用的形式回答问题。

- 先给出答案，而不是推理过程
- 保持简短——如果需要完整解释，提议在任务结束后再深入展开
- 如果问题涉及当前正在处理的文件或代码，请精确引用（必要时给出文件路径和行号）
- 如果回答需要读取文件，就读取它——但只读，绝不写入

按以下格式回应：

```
ASIDE: [简要复述问题]

[你的回答]

— 回到任务：[对正在进行的工作的一句话描述]
```

### 第 3 步：恢复主任务

给出回答后，立即从任务暂停的确切位置继续执行活跃任务。除非旁支回答暴露了阻塞项，或有理由重新考虑当前方案（参见边界情况），否则无需请求许可即可恢复。

## 边界情况

**未提供问题（`/aside` 后面没有任何内容）：**
回应：
```
ASIDE: 未提供问题

你想了解什么？（提出你的问题，我会在不丢失当前任务上下文的情况下回答）

— 回到任务：[对正在进行的工作的一句话描述]
```

**问题揭示了当前任务的潜在问题：**
在恢复之前明确标记出来：
```
ASIDE: [回答]

WARNING: 注意：这个回答表明当前方案存在 [问题]。想在继续之前先处理它，还是按原计划进行？
```
等待用户决定后再恢复。

**问题实际上是任务转向（而非旁支问题）：**
如果问题暗示要改变正在构建的内容（例如 `/aside 其实，我们还是改用 Redis 吧`），请澄清：
```
ASIDE: 这听起来像是方向调整，而不只是一个旁支问题。
你想：
  (a) 仅将其作为信息参考，保持当前计划
  (b) 暂停当前任务并改变方案
```
等待用户的回答——不要擅自假设。

**问题涉及当前打开的文件或代码：**
基于实时上下文回答。如果该文件在会话中先前已读取过，直接引用它。如果没有，现在读取它（只读），并以 文件：行号 的形式给出引用。

**没有活跃任务（调用 `/aside` 时没有任何进行中的工作）：**
仍使用标准包裹格式，以保持响应结构一致：
```
ASIDE: [简要复述问题]

[你的回答]

— 回到任务：没有可恢复的活跃任务
```

**问题需要长篇回答：**
简洁地给出要点式回答，然后提议：
```
以上是简短版本。想在我们完成 [当前任务] 之后获得更深入的解释吗？
```

**连续多个 `/aside` 问题：**
按顺序逐一回答。回答完最后一个之后，恢复主任务。不要在一连串旁支问答之间丢失任务状态。

**旁支回答表明需要进行代码修改：**
记下所需的修改，但不要在旁支问答期间做出修改：
```
ASIDE: [回答]

 值得修复：[应修改的内容]。除非你想现在处理，否则我会在当前任务结束后标记此事。
```

**问题含糊或过于宽泛：**
提出一个澄清问题——用最短的问题获取回答所需的信息。不要一次提出多个问题。

## 输出示例

```
用户：/aside fetchWithRetry() 到底做了什么？

ASIDE: fetchWithRetry() 做了什么？

fetchWithRetry()（src/api/retry.ts:12）以指数退避（250ms → 500ms → 1s）最多尝试
请求 3 次。仅对 5xx 响应和网络错误进行重试——4xx 错误被视为最终结果，不会重试。

— 回到任务：重构 src/middleware/auth.ts 中的 auth 中间件
```

```
用户：/aside 我们采用的方案是线程安全的吗？

ASIDE: 当前方案是线程安全的吗？

不是——src/cache/store.ts:34 中的共享缓存对象在没有加锁的情况下被修改。
在并发请求下这是一个竞态条件。在单进程 Node.js 服务器中风险较低，
但在 worker 线程或集群模式下会成为真正的问题。

WARNING: 注意：这可能会影响我们正在构建的功能。想现在处理，还是继续并在后续任务中修复？
```

## 注意事项

- 旁支问答期间绝不修改文件——仅限只读访问
- 旁支问答是对话暂停，不是新任务——原任务必须始终恢复
- 回答保持聚焦：目标是快速为用户解除阻塞，而不是长篇授课
- 如果旁支问答引发更大的讨论，先完成当前任务，除非它暴露了阻塞项
- 旁支问答不会保存到会话文件中，除非与任务结果明确相关
